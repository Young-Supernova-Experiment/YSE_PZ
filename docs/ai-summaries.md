# AI summaries and summary search

SkyPortal-parity umbrella #294 (#295 `Transient.summary` + version history + human editing, #296 the
summariser service with a configurable LLM provider, #297 embeddings and `/summary_search/`).
Every transient can carry a short, current summary: what it is, its redshift and classification,
what has been done, and the open questions. A person can write or edit it; the **summariser** can
write it from the transient's own data through a pluggable provider; every version is kept with
its provenance; and the summaries are searchable in natural language.

The design follows SkyPortal's summary and summary-search features (BSD-3-Clause) in spirit
(a summary column, a version history with the origin of each version, one embedding per object,
cosine search over the embeddings). No SkyPortal code is copied.

## Concepts

| term | meaning |
|---|---|
| `Transient.summary`, `Transient.summary_modified` | the current text and when it changed. Read-only on `/api/transients/`; writes go through the summary endpoints below so every version is kept. |
| `TransientSummaryHistory` (`YSE_App/models/summary_models.py`) | one row per version: `text`, `source` (`ai` / `human`), `provider`, `model_name`, `prompt_version`, `inputs_hash` (sha256 of the gathered context), `run` (the `ExternalServiceRun`), `is_current`, audit fields. Tracked by `auditlog`. |
| `TransientSummaryEmbedding` | one vector per transient (float32 blob, L2-normalised) with the embedder's `model_name` and the `text_hash` it was computed from. Refreshed on every summary write. |
| `TransientSummaryPreference` | the per-user opt-in (`ai_enabled`). Without it a user sees and edits summaries but never triggers the LLM. |
| the `ai_summary` service | an `ExternalService` of kind `summary` (#265). Its `groups` are the group side of the opt-in (empty = every opted-in user), `max_runs_per_user_per_day` the cap (staff exempt), `credential` the provider key, `default_params` per-service overrides (`provider`, `model`, `api_base`, `max_tokens`, `temperature`, `embedding_api_base`, `embedding_model`). |
| provider | `template` (default): a deterministic summary rendered from the gathered context, no network, no key. `openai`: any OpenAI-compatible `/chat/completions` server. `anthropic`: the Anthropic Messages API. `YSE_App/services/llm.py`. |

## The Summary card

The Summary tab of every transient page has a **Summary** card at the top of the right-hand column
(fragment `transient_detail/<id>/summary_fragment/`, loaded with the page). It shows the current
text and its provenance ("Generated by `<model>` (`<provider>`, prompt v1), inputs `<hash>`,
requested by `<user>` on `<date>`" or "Written by `<user>`"), then:

* **Generate / Regenerate**: queues a summariser run (`transient_detail/<id>/summary_generate/`).
  Shown only to users who ticked **Enable AI summaries for me** on the card *and* whom the service's
  `groups` allow (staff always pass the group test, never the opt-in). The card polls every few
  seconds while a run is active and shows the error of a failed run; the requester also gets an
  in-app notification when a run fails. A second click while a run is active answers 409; the daily
  cap answers 429.
* **Edit**: a textarea; saving stores a `human` version (`transient_detail/<id>/summary_edit/`).
  Everyone who can see the transient may edit (`SUMMARY_EDIT_STAFF_ONLY: True` restricts it to staff
  and holders of the `YSE_App.can_edit_summary` permission).
* **History (n)**: every version, newest first, with its source, author and full text.
* The opt-in checkbox (`transient_detail/<id>/summary_optin/`) and a link to the search page.

Tables of transients (dashboards, `/search/`) show the first line of the summary as the tooltip of
the name link.

## What the summariser sees

`gather_context(transient, viewer=None)` (`YSE_App/services/summaries.py`) collects: name and
other names, coordinates, discovery date, status and survey, tags, the four classes, redshift
(+ error and source, falling back to the host), host name / redshift / photo-z, MW E(B-V), the
PhotStat numbers (#268: detections, first / peak / last magnitude and band, rise and decay rates,
deepest limit, time to non-detection), the spectra (date, telescope / instrument, redshift, phase,
notes), the follow-up requests (status, resource, window), the annotation verdicts (#316) and the
last `SUMMARY_MAX_COMMENTS` comments.

Visibility rule: **only collaboration-wide content is ever summarised**: public comments with no
group audience, spectra / follow-ups / annotations with no group restriction. With a `viewer` the
same rows are additionally filtered by that user's visibility, so a run never contains a comment
the requesting user cannot see; the nightly batch runs with `viewer=None`, the collaboration-wide
subset only. Private (group-restricted or non-public) comments never reach a provider and never
appear in a summary that every viewer of the transient can read.

`build_prompt(context)` is a fixed template (`SYSTEM_PROMPT` + one line per fact + the comments,
newest first); it is deterministic for a given context and cut to `SUMMARY_PROMPT_MAX_CHARS` by
dropping the oldest comments first. `inputs_hash(context)` is stored with every generated version.
The `template` provider skips the prompt and renders `render_template_summary(context)`.

## Providers and the key

`LLM_PROVIDER` under `[llm]` in `settings.ini` picks the default backend; the service row's
`default_params["provider"]` overrides it. The API key is **never** in `settings.ini`: it is the
`api_key` (or `token`) entry of an **Encrypted credential** (#264, admin > Encrypted credentials)
attached to the `ai_summary` service, or, failing that, of the credential whose name or service
slug equals `LLM_CREDENTIAL` (default `llm`).

| provider | endpoint | model | notes |
|---|---|---|---|
| `template` | none | `template-v1` | default; deterministic; works everywhere |
| `openai` | `LLM_API_BASE` (default `https://api.openai.com/v1`) `/chat/completions` | `LLM_MODEL` (required) | also vLLM, Ollama, LM Studio, llama.cpp, Azure-style gateways; `LLM_TEMPERATURE` is sent when set |
| `anthropic` | `LLM_API_BASE` (default `https://api.anthropic.com`) `/v1/messages` | `LLM_MODEL`, default `LLM_ANTHROPIC_DEFAULT_MODEL` = `claude-opus-5-5` | `anthropic-version: 2023-06-01`; no sampling parameters are sent; a `refusal` stop reason fails the run with the category |

Everything is plain HTTP through `requests`; no provider SDK is required in the production venv.
Calls happen only inside a job-queue worker (`external_service.run` jobs, #263), never in a web
request.

### Embeddings

`/summary_search/` needs one vector per summary. With `LLM_EMBEDDING_API_BASE` +
`LLM_EMBEDDING_MODEL` (an OpenAI-compatible `/embeddings` endpoint, same key lookup) the vectors
come from there; without them the built-in **hashed bag-of-words embedder** (`local-hash-v1`, 256
dimensions, unigrams + bigrams, signed hashing, L2-normalised) is used. It is lexical, not
semantic: "young Type II with a spectrum from Keck" finds summaries that use those words. Vectors
carry the embedder's name and are only ever compared with vectors of the same name; after changing
the embedder run `manage.py register_summary_service --rebuild-embeddings`.

## Summary search (#297)

`/summary_search/?q=...` (and the box **Ask the summaries…** in the page header next to the name
search) embeds the query, ranks every stored vector of the current embedder by cosine similarity
(numpy over a matrix cached in the process and rebuilt when the table changes; 5 000 vectors rank
in a few milliseconds), drops matches below `SUMMARY_SEARCH_MIN_SCORE`, filters the candidates by
the user's transient access (`filter_transients_by_user_access`) and lists the top
`SUMMARY_SEARCH_LIMIT` with a snippet around the first matching word. With no stored vectors for
the current embedder, or `SUMMARY_SEARCH_MODE: text`, it falls back to `summary__icontains`.

## Nightly batch

`SummaryRefresh` (`YSE_App/data_ingest/Summary_Jobs.py`, in `CRON_CLASSES`) is a no-op until
`SUMMARY_BATCH_CRON_ENABLED: True`. Every `SUMMARY_BATCH_CRON_MINUTES` (1440) it queues one
`summaries.refresh_stale` job; the job queues a collaboration-wide (`batch`) summariser run for
every transient with a new public comment, spectrum, follow-up or edit in the last
`SUMMARY_BATCH_HOURS` whose summary is older than that activity (at most `SUMMARY_BATCH_MAX` per
pass, skipping transients with a run in flight). Batch runs are stamped with the service's creator
and are exempt from the daily cap. `manage.py run_jobs` (or the `RunQueuedJobs` cron) executes them.

## API

| call | what |
|---|---|
| `GET /api/transients/<id>/summary/` | `{summary, summary_modified, current, history: [versions], run}` |
| `PATCH /api/transients/<id>/summary/` `{"text": ...}` | a human version (same permission as the card's Edit) |
| `POST /api/transients/<id>/summary/generate/` | queue a run: 202 `{run, status}`; 403 without the opt-in / group; 409 while one runs; 429 at the cap |
| `GET /api/summary_search/?q=...&limit=N` | `{query, mode, model, results: [{transient, name, slug, status, spec_class, redshift, score, snippet, summary_modified}]}` |

`summary` is also present (read-only) on `/api/transients/<id>/`.

## Settings (`settings.ini`, `[llm]`, all optional)

| key | default | meaning |
|---|---|---|
| `LLM_PROVIDER` | `template` | `template`, `openai` or `anthropic` (env `YSE_LLM_PROVIDER` overrides) |
| `LLM_MODEL` | blank | model for `openai` (required) / `anthropic` |
| `LLM_ANTHROPIC_DEFAULT_MODEL` | `claude-opus-5-5` | used when the provider is `anthropic` and `LLM_MODEL` is blank |
| `LLM_API_BASE` | per provider | endpoint base |
| `LLM_CREDENTIAL` | `llm` | name or service slug of the Encrypted credential with the key |
| `LLM_MAX_TOKENS` / `LLM_TEMPERATURE` / `LLM_HTTP_TIMEOUT_SECONDS` | 600 / unset / 60 | request parameters (temperature is sent to `openai` only) |
| `LLM_EMBEDDING_API_BASE`, `LLM_EMBEDDING_MODEL` | blank | remote embeddings; both blank = local hashed embedder |
| `SUMMARY_MAX_COMMENTS`, `SUMMARY_PROMPT_MAX_CHARS` | 15, 12000 | context and prompt caps |
| `SUMMARY_RUN_STALE_MINUTES` | 30 | a pending / running run older than this is marked failed when the card loads |
| `SUMMARY_EDIT_STAFF_ONLY` | False | restrict human edits to staff / `can_edit_summary` |
| `SUMMARY_SEARCH_LIMIT`, `SUMMARY_SEARCH_MODE`, `SUMMARY_SEARCH_MIN_SCORE` | 25, `embedding`, 0.1 | search page |
| `SUMMARY_BATCH_CRON_ENABLED`, `SUMMARY_BATCH_CRON_MINUTES`, `SUMMARY_BATCH_HOURS`, `SUMMARY_BATCH_MAX` | False, 1440, 24, 200 | nightly batch |

## Operator steps

1. Migrate (`manage.py migrate`; the Deploy Stack workflow does it). No new Python dependency.
2. Register the service: `python manage.py register_summary_service` (enabled, `template`
   provider; add `--group YSE` to limit generation to a group, `--cap 20` for a per-user daily cap,
   `--disabled` to create it switched off). Everything is editable afterwards in
   admin > External services > `ai_summary`.
3. Optional, to use a real LLM: create an Encrypted credential (admin > Encrypted credentials,
   kind Generic, service `llm`, name e.g. `Anthropic key`, secret `{"api_key": "..."}`), then either
   set `LLM_PROVIDER: anthropic` (or `openai` + `LLM_MODEL`) under `[llm]` in `settings.ini` and
   restart Apache, or store the provider on the service row:
   `python manage.py register_summary_service --provider anthropic --credential "Anthropic key"`.
   The card shows "Summariser not configured (...)" until the provider, model and key line up.
4. Users tick **Enable AI summaries for me** on any transient page; nothing is generated for a user
   who has not.
5. Optional: `SUMMARY_BATCH_CRON_ENABLED: True` for the nightly batch (needs the job runner,
   docs/background-jobs.md). The Ziggy web venv still needs `manage.py run_jobs` or the
   `RunQueuedJobs` cron to execute runs at all; with `JOB_RUNNER_INLINE` off, a click on Generate
   shows the spinner until the next runner pass.
6. After switching embedders: `python manage.py register_summary_service --rebuild-embeddings`.

## Tests

`YSE_App/tests/test_ai_summaries.py` (both database vendors): the gathered context and its
visibility rules, the deterministic prompt / template / hash, the history semantics, the provider
adapters against mocked HTTP (including an Anthropic refusal and the absence of sampling
parameters), the queue path end to end, failures on the run + notification, the opt-in, group and
cap gates, the card fragment and actions, the DRF endpoints, the table tooltip, the search ranking
(the "young Type II with a spectrum from Keck" fixture ranks first), visibility, the text fallback,
the ranking budget (5 000 x 256 in well under 500 ms), the nightly batch, the cron gate and the
management command. LLM APIs are never called from tests.
